## 2주차 과제

### 이슈 1: 클래스 네이밍 및 스타일 적용
* **오류 상황:** 요약 카드와 상세 카드에서 파트별(Frontend, Backend, Design)로 다른 스타일(색상 등)을 적용해야 하는데, 클래스 이름을 어떻게 지어야 효율적일지 혼란이 발생함.
* **원인:** 처음에 `part-frontend` 등 단일 클래스로만 묶어서 처리하려다 보니, 모든 카드에 들어가는 '공통 스타일'과 파트별 '개별 스타일'을 분리해서 CSS로 관리하기가 어려웠음.
* **시도한 해결 방법:** 공통 클래스와 역할을 구분하는 단일 클래스를 나누어 적용할 방법을 고민함.
* **최종 해결 방법:** `member-role` (공통 레이아웃/폰트)과 `member-role--frontend` (파트별 색상)처럼 공통 클래스와 수식어(Modifier) 클래스를 함께 사용하는 방식으로 HTML 구조를 변경함. 
  * 뱃지 역시 `badge`와 `badge--react` 등으로 분리하여 CSS 유지보수성과 확장성을 높임.

## 3주차 과제

### 이슈 1: 유효성 검사 에러 메시지
* **오류 상황:** 에러 메시지에 `hidden` 처리를 했음에도 불구하고 화면을 처음 열었을 때부터 에러 문구가 노출되거나, JS로 모든 유효성 검사를 직접 제어하려다 보니 코드가 복잡해짐.
* **원인:** `type`, `id`, `class` 선택자를 일관성 없이 혼용하면서 스크립트 제어가 얽혔고, 브라우저의 기본 폼 검증 기능을 무시한 채 수동으로 모두 처리하려 했기 때문.
* **시도한 해결 방법:** CSS에 `!important`를 부여하여 강제로 숨김 처리를 시도함.
* **최종 해결 방법:** 불필요하게 비대해진 JS 커스텀 검사 로직을 걷어내고, HTML5 폼(Form)에서 기본적으로 제공하는 내장 유효성 검사(기본 에러 메시지)를 적극 활용하는 방식으로 타협하여 코드를 직관적이고 깔끔하게 해결함.

### 이슈 2: 초기화 로직 비대화 (스파게티 코드 방지 및 모듈화)
* **오류 상황:** 페이지 로드 완료 시 이벤트를 바인딩하기 위해 `document.addEventListener('DOMContentLoaded', ...)` 내부에 모든 버튼과 폼의 이벤트 리스너 로직을 작성했더니 코드가 너무 길어지고 가독성이 심각하게 저하됨.
* **원인:** 스크립트의 초기 진입점에 수많은 이벤트 등록 로직이 한데 섞이면서 코드의 구조가 지저분해짐.
* **최종 해결 방법:** 이벤트 리스너를 등록하는 역할만 전담하는 `initEventListeners()` 함수를 별도로 밖으로 빼내어 분리함. 초기화 블록에서는 해당 함수를 호출만 하도록 변경하여 코드의 가독성을 높이고 유지보수가 쉬운 구조로 리팩토링함.

## 4주차 과제

### 이슈 1: 버튼 이벤트 리스너 중복 할당
* **오류 상황:** 랜덤 1명 추가, 5명 추가 등 여러 버튼에 이벤트를 부여할 때 각각 `getElementById`를 사용하여 개별적으로 바인딩함.
* **원인:** 버튼의 기능이 늘어날 때마다 중복 코드가 발생하여 비효율적임.
* **최종 해결 방법:** 공통 클래스(`.fetch-btn`)를 부여하고 `querySelectorAll`로 한 번에 가져와 반복문으로 처리함. 이때 `dataset`을 활용하여 몇 명(`count`)인지, 어떤 버튼(`clickedBtn`)인지를 동적으로 매개변수로 넘겨주도록 개선함.

### 이슈 2: 데이터 더블 렌더링 (총 인원수 오류)
* **오류 상황:** 새로고침 기능을 구현하기 위해 하드코딩된 HTML 데이터를 JS 배열(`lionMembers`)로 옮겼는데, 화면에 카드가 2배(8명)로 늘어나서 출력됨.
* **원인:** JS가 배열을 바탕으로 카드를 그려낸 직후, 3주차에 만들어 두었던 `initDataFromHTML()` 함수가 동작하면서 '화면에 그려진 데이터'를 다시 읽어와 배열에 억지로 집어넣는(push) 과거 코드와의 충돌이 발생함.
* **최종 해결 방법:** 데이터를 HTML에서 읽어오는 구시대적 함수(`initDataFromHTML`)를 완전히 삭제하고, 오직 JS 배열 하나로만 UI를 통제하도록 단일 진실 공급원(SSOT) 체제로 구조를 개편함.

### 이슈 3: API 로직 중복 및 재시도 옵션 누락 버그
* **오류 상황:** 랜덤 값 채우기, 랜덤 추가, 전체 새로고침 세 기능이 모두 API 호출 로직을 중복으로 구현하고 있었음. 함수를 통합한 후 '랜덤 값 채우기' 실패 시 '재시도'를 누르면 값이 폼에 채워지지 않고 무작정 카드가 추가되어버리는 버그 발생.
* **원인:** 데이터를 가져와서 변환하는 흐름은 같으나, 마지막 DOM 처리 방식만 다름. 재시도 버튼을 눌렀을 때 마지막으로 실행했던 '작업의 종류(옵션)'를 기억하지 못하고 기본 동작(추가)을 수행했기 때문.
* **시도한 해결 방법:** 함수 구조에 문제가 있다고 생각해 새로운 마스터 함수(`executeLionFetch`)를 만들어서 구조를 완전히 뒤엎어보려 했으나 기존 흐름과 꼬여서 롤백함.
* **최종 해결 방법:** 하나의 비동기 함수(`fetchRandomLions`)에 `options` 파라미터(객체)를 도입하여 역할을 분기함(`fillForm: true`, `refresh: true` 등). 재시도 버그를 완벽히 해결하기 위해 `lastOptions`라는 전역 변수를 선언하고, 각 기능을 실행할 때마다 해당 옵션을 캐싱해 두었다가 재시도 시 함께 넘겨주도록 수정하여 코드 중복을 통합하고자 함.



### 추가 : 상태 기반 렌더링
* **개선 배경:** 데이터가 변경될 때마다 DOM을 개별적으로 조작(추가/삭제/필터링)하다 보니 로직이 파편화되고 화면과 데이터의 불일치 위험이 컸음.
* **해결 과정:** `render()`라는 통합 함수 구축
* **결과:** 오직 배열(`lionMembers`) 데이터만 변경하고 `render()`를 호출하면 필터, 정렬, 검색, UI 렌더링, 인원수 갱신이 한 번에 완벽하게 동기화되도록 코드를 전면 개편하여 시스템의 안정성과 유지보수성을 극대화함.
